# CONTRACTS.md

**Frozen.** Every API shape in Paygent is defined here. Owner: Nikhil.

If you need a field name, type or enum value changed, raise it — do not edit this file and do
not silently reshape data at either end. Backend responses, frontend consumers and
`frontend/src/mock/*.json` must all agree with this document. `/contract-check` verifies that.

---

## 0. Conventions

These apply to every shape below without exception.

**Money**
- Always a JSON `number` (Python `float`), always in **rupees**, always suffixed `_inr`.
- No paise. No strings. No `Decimal`. No integer minor units.
- `1499.0`, never `"1499.00"`, never `149900`.

**Time**
- ISO 8601, UTC, trailing `Z`: `"2026-08-27T18:30:00Z"`.
- Durations are integer seconds, suffixed `_seconds`; latencies are `_ms`.

**Deterministic vs modelled — the hard one**
- Every rupee figure that could be either carries a sibling `basis` field:
  `"deterministic"` or `"modelled"` (lowercase, exactly these two values).
- `deterministic` = read off ledger rows that exist. `modelled` = produced by a scorer.
- **The two are never added together.** Not in a response field, not in a chart series, not in
  a log line. Where a total is needed, the contract returns *two* totals. Any endpoint that
  returns a single blended at-risk number is a contract violation.

**Enums**
- Serialised as uppercase strings, except `basis` and `proposed_by`, which are lowercase.
- Consumers must tolerate an unknown enum value by displaying it verbatim rather than
  crashing. `UNCLASSIFIED_BREAK` exists precisely because the state space is open.

**Identifiers** — opaque prefixed strings, never parsed by the frontend.

| Prefix | Entity |
|---|---|
| `cus_` | customer |
| `ses_` | checkout session |
| `pay_` | payment |
| `ord_` | order |
| `mdt_` | mandate |
| `case_` | recovery case |
| `act_` | action |
| `cnv_` | conversation |

**Nulls** — every documented field is always present. Unknown or not-applicable values are
`null`, never omitted, never `""`. Arrays are `[]`, never `null`.

**Confidence** — float `0.0`–`1.0`, two decimals.

## 1. Enums

### The four ledgers

```
PaymentState      INITIATED | PENDING | AUTHORIZED | CAPTURED | FAILED | REFUNDED
OrderState        MISSING | CREATED | CONFIRMED | FULFILLED | CANCELLED
InventoryState    NOT_APPLICABLE | AVAILABLE | RESERVED | SHIPPED | RETURNED
AccountingState   NOT_BOOKED | DEFERRED | REVENUE_RECOGNIZED | REVERSED
```

SaaS rows always use `InventoryState.NOT_APPLICABLE` — never `null`, never `""`.

`INITIATED`, `PENDING` and `AUTHORIZED` are the non-terminal payment states. They are defined
once, in `backend/ledgers/states.py::NON_TERMINAL_PAYMENT_STATES`, and consumed by
`backend/guardrails/blocks.py`. Do not redefine that set anywhere else.

### BusinessType

```
ECOMMERCE | SAAS
```

### BreakType

```
CHECKOUT_ABANDONED                 checkout initiated, no payment attempt, past dwell
PAYMENT_PENDING_WEBHOOK_MISSING    payment pending, no order, past dwell        (Scenario 2)
AUTHORIZED_NOT_CAPTURED            authorised, never captured, past dwell
ORPHAN_PAYMENT_NO_ORDER            money captured, no order record              (Scenario 1)
REVENUE_NOT_BOOKED                 captured and confirmed, never booked
FULFILMENT_STALLED                 paid and reserved, never shipped
REFUND_WITHOUT_CANCELLATION        refunded but order still active + recognised (Scenario 3)
REFUND_AFTER_SHIPMENT              refunded after goods shipped                 (Scenario 3, e-comm)
PAYMENT_ON_CANCELLED_ORDER         captured against a cancelled order
DUPLICATE_PAYMENT                  two captured payments, one intent
MANDATE_DEBIT_FAILED               autopay debit failed, subscription in grace
MANDATE_UNRETRYABLE                failure is structural — revoked, expired, over cap
SETTLEMENT_SHORT_PAID              settled net is below expected net of known fees
STATUTORY_CREDIT_UNCLAIMED         GST credit note / TCS credit not reclaimed
UNCLASSIFIED_BREAK                 ledger combination outside the legal set
```

`UNCLASSIFIED_BREAK` is a feature, not a fallback. The engine enumerates what is *legal* and
treats everything else as a break, which is why it catches failures nobody coded for. Consumers
must render it as a first-class case, not as an error.

### CaseStatus

```
OPEN | INVESTIGATING | AWAITING_APPROVAL | BLOCKED | RESOLVED | EXPIRED
```

`BLOCKED` means a blocking guardrail stopped the action. It is a terminal-for-now state with a
visible reason, not a failure.

### Resolver

```
RECONCILIATION | SEQUENCER | CART
```

### Tier

Integer `0`, `1`, `2`. Set by `backend/guardrails/engine.py`.

| tier | tier_label | meaning |
|---|---|---|
| 0 | `AUTO` | execute without a human |
| 1 | `APPROVE` | propose, hold for human approval |
| 2 | `INVESTIGATE_ONLY` | never touches money; surface for a human to look at |

A blocking guardrail failure forces tier `2` regardless of confidence.

### ActionType / ActionStatus

```
ActionType    CREATE_ORDER | ISSUE_REFUND | RETRY_DEBIT | POLL_PAYMENT_STATUS
            | CANCEL_ORDER | ISSUE_CREDIT_NOTE | SEND_MESSAGE | OFFER_DISCOUNT
            | NO_ACTION

ActionStatus  PROPOSED | APPROVED | BLOCKED | EXECUTED | FAILED
```

`NO_ACTION` is a legitimate, and sometimes the correct, outcome — Scenario 2 resolves to it.

### MandateState

```
ACTIVE | PAUSED | REVOKED | EXPIRED
```

### FailureReasonCode

```
INSUFFICIENT_FUNDS | BANK_TIMEOUT | ISSUER_DECLINED | TECHNICAL_DECLINE
MANDATE_REVOKED | MANDATE_EXPIRED | AMOUNT_EXCEEDS_MANDATE_CAP
AFA_NOT_COMPLETED | CUSTOMER_CANCELLED
```

`MANDATE_REVOKED`, `MANDATE_EXPIRED` and `AMOUNT_EXCEEDS_MANDATE_CAP` are structurally
unretryable. `backend/sequencer/router.py` must never spend an attempt on them.

### basis

```
deterministic | modelled
```

## 2. Core objects

### LedgerSnapshot

The four ledgers at a point in time, plus how long they have disagreed.

```json
{
  "payment": "PENDING",
  "order": "MISSING",
  "inventory": "AVAILABLE",
  "accounting": "NOT_BOOKED",
  "age_seconds": 5400,
  "observed_at": "2026-08-27T18:30:00Z"
}
```

`age_seconds` is how long this combination has held. It is what turns a legal state into a
break: `PENDING + MISSING` is healthy for a customer mid-checkout and becomes
`PAYMENT_PENDING_WEBHOOK_MISSING` only past its dwell limit.

### GuardrailResult

Never a bare bool. Never an exception on the normal blocking path.

```json
{
  "name": "refund_requires_terminal_payment",
  "passed": false,
  "blocking": true,
  "message": "The payment is still PENDING. In India the acquirer must auto-reverse an unconfirmed UPI payment to the customer within T+5 days. Refunding from merchant balance now risks paying this customer twice.",
  "evaluated_at": "2026-08-27T18:30:01Z"
}
```

| field | meaning |
|---|---|
| `name` | asserts the *safe state*, not the failure: `no_duplicate_order_exists`, not `check_duplicates` |
| `passed` | did the safe condition hold |
| `blocking` | `true` — the action cannot proceed under any circumstance. `false` with `passed:false` downgrades the tier but does not forbid |
| `message` | plain English, reason included. This is read aloud on stage — it is a sentence a finance person understands, not a log line |

Guardrails are pure deterministic Python: no LLM calls, no network calls, offline and instant.

### Action

What a resolver proposes, and what the deterministic layer decided about it.

```json
{
  "action_id": "act_00f3",
  "type": "ISSUE_REFUND",
  "status": "BLOCKED",
  "amount_inr": 2499.0,
  "basis": "deterministic",
  "proposed_by": "reconciliation",
  "decided_by": "guardrails",
  "params": { "payment_id": "pay_881f2" },
  "blocked_by": ["refund_requires_terminal_payment"],
  "idempotency_key": "recon:pay_881f2:ISSUE_REFUND",
  "created_at": "2026-08-27T18:30:01Z"
}
```

- `proposed_by` is lowercase: `"reconciliation"`, `"cart"`, `"sequencer"` or `"deterministic"`.
- `amount_inr` is **never chosen by an LLM.** An agent may propose the action; the amount is
  computed by deterministic code. `null` where the action moves no money.
- `blocked_by` lists `GuardrailResult.name` values. `[]` when nothing blocked it.
- `idempotency_key` is derived from the source record, so a retried agent run can never create
  two orders or two refunds.

### RecoveryCase

One case object per detected break. The spine of the whole system.

```json
{
  "case_id": "case_0417",
  "created_at": "2026-08-27T18:12:00Z",
  "updated_at": "2026-08-27T18:30:01Z",
  "business_type": "ECOMMERCE",
  "break_type": "PAYMENT_PENDING_WEBHOOK_MISSING",
  "status": "BLOCKED",
  "title": "Customer debited, no order created",
  "summary": "UPI payment pending for 90 minutes. Customer reports the amount left their account. No order exists.",

  "customer_id": "cus_1042",
  "session_id": "ses_7731",
  "payment_id": "pay_881f2",
  "order_id": null,
  "mandate_id": null,

  "rupees_at_risk_inr": 2499.0,
  "basis": "deterministic",
  "confidence": 0.92,

  "deadline_at": "2026-09-01T18:12:00Z",
  "deadline_reason": "T+5 acquirer credit adjustment window closes",
  "priority_score": 421.3,

  "resolver": "RECONCILIATION",
  "tier": 2,
  "tier_label": "INVESTIGATE_ONLY",

  "ledger_snapshot": { "...": "LedgerSnapshot" },
  "guardrail_checks": [ { "...": "GuardrailResult" } ],
  "actions": [ { "...": "Action" } ],
  "trace_available": true
}
```

**`priority_score`** — computed deterministically so backend and frontend sort identically.
No LLM input. Definition, and this is normative:

```
DEADLINE_HORIZON_SECONDS = 604800            # 7 days

seconds_left = (deadline_at - now).total_seconds()
urgency      = 1.0 if seconds_left <= 0 else
               clamp(1.0 - (seconds_left / DEADLINE_HORIZON_SECONDS), 0.05, 1.0)

priority_score = round(rupees_at_risk_inr * urgency * confidence, 2)
```

This is what makes the case feed a prioritised queue rather than a log. Default sort everywhere
is `priority_score` descending.

**Money rules on this object:** `rupees_at_risk_inr` means nothing without its `basis`. Never
sum `rupees_at_risk_inr` across cases of differing `basis` — sum within a basis and return two
figures.

## 3. REST endpoints

Base path `/api`. All responses `application/json`.

### GET /api/summary

Powers Command Center. Contains no AI output — every figure traces to ledger rows or a
declared scorer.

```json
{
  "generated_at": "2026-08-27T18:30:00Z",
  "currency": "INR",
  "counters": {
    "recovered_inr": 843200.0,
    "awaiting_approval_inr": 128400.0,
    "deterministic_at_risk_inr": 620000.0,
    "modelled_at_risk_inr": 4100000.0
  },
  "case_counts": {
    "open": 412,
    "investigating": 18,
    "awaiting_approval": 47,
    "blocked": 9,
    "resolved": 124
  },
  "waterfall": {
    "gross_intended_inr": 12400000.0,
    "realised_inr": 8900000.0,
    "buckets": [
      {
        "id": "B1",
        "stage": "Checkout initiated → Payment attempted",
        "entering_inr": 12400000.0,
        "leaked_inr": 2100000.0,
        "exiting_inr": 10300000.0,
        "basis": "deterministic",
        "case_count": 1840,
        "detail": "Sessions with a cart but no payment attempt"
      }
    ]
  }
}
```

**The four counters are four separate fields and stay that way.**
`deterministic_at_risk_inr` and `modelled_at_risk_inr` are rendered as two labelled figures.
Adding them produces a number that means nothing, and a judge will look for exactly this.

**Waterfall buckets — exactly six, in this order, with these ids:**

| id | stage | source | basis |
|---|---|---|---|
| `B1` | Checkout initiated → Payment attempted | abandoned `checkout_sessions` | deterministic |
| `B2` | Payment attempted → Payment authorised | `payments` in `FAILED` | deterministic |
| `B3` | Payment authorised → Order recognised | `CAPTURED` with `OrderState.MISSING` | deterministic |
| `B4` | Order recognised → Settled to bank | `settlements` gross vs net | deterministic where settled, modelled where pending |
| `B5` | Settled to bank → Net of reversals | refunds and chargebacks | deterministic |
| `B6` | Net of reversals → Realised | unclaimed statutory credits | modelled |

**Chain invariants — checkable, and the frontend may assume them:**

```
buckets[0].entering_inr        == waterfall.gross_intended_inr
buckets[i].exiting_inr         == buckets[i+1].entering_inr
buckets[i].entering_inr - buckets[i].leaked_inr == buckets[i].exiting_inr
buckets[5].exiting_inr         == waterfall.realised_inr
```

A bucket carries exactly one `basis`. A bucket whose sources are mixed reports `"modelled"` and
says so in `detail` — it never averages the two into a figure presented as deterministic.

### GET /api/cases

Query parameters, all optional:

| param | type | default |
|---|---|---|
| `status` | CaseStatus | all |
| `break_type` | BreakType | all |
| `resolver` | Resolver | all |
| `business_type` | BusinessType | all |
| `basis` | basis | all |
| `limit` | int | `50` |
| `offset` | int | `0` |
| `sort` | `-priority_score` \| `-created_at` \| `-rupees_at_risk_inr` | `-priority_score` |

```json
{
  "items": [ { "...": "RecoveryCase" } ],
  "total": 610,
  "limit": 50,
  "offset": 0,
  "totals_at_risk": {
    "deterministic_inr": 620000.0,
    "modelled_inr": 4100000.0
  }
}
```

`totals_at_risk` reflects the *filtered* set. Two figures, never one.

### GET /api/cases/{case_id}

A single `RecoveryCase`, fully populated — `ledger_snapshot`, `guardrail_checks` and `actions`
are always present. `404` with `CASE_NOT_FOUND` if unknown.

### GET /api/mandates

```json
{
  "items": [
    {
      "mandate_id": "mdt_0091",
      "customer_id": "cus_1042",
      "state": "ACTIVE",
      "cap_inr": 25000.0,
      "debit_amount_inr": 1499.0,
      "requires_afa": false,
      "cycle": "2026-08",
      "next_debit_at": "2026-08-29T02:30:00Z",
      "attempts_used": 1,
      "attempts_remaining": 3,
      "last_failure_reason": "INSUFFICIENT_FUNDS",
      "at_risk_inr": 1499.0,
      "basis": "deterministic",
      "router_verdict": {
        "retryable": true,
        "reason": "Insufficient funds is a timing failure, not a structural one.",
        "checks": [ { "...": "GuardrailResult" } ]
      },
      "predicted_success": 0.61,
      "predicted_basis": "modelled"
    }
  ],
  "total": 2000
}
```

`requires_afa` is `debit_amount_inr > 15000.0`. Above that threshold UPI Autopay needs customer
OTP approval every cycle — there is no subscription exemption.

`attempts_remaining` is bounded by the NPCI limit of 4 per cycle (1 original + 3 retries). It is
a scarce, irreversible resource; `router_verdict.retryable = false` is how we avoid burning one.

### GET /api/mandates/{mandate_id}/plan

The naive-vs-sequenced toggle on Mandate Board.

```json
{
  "mandate_id": "mdt_0091",
  "cycle": "2026-08",
  "retryable": true,
  "router_verdict": { "...": "as above" },
  "naive": {
    "strategy": "NAIVE",
    "attempts": [
      {
        "attempt_no": 1,
        "slot_at": "2026-08-29T04:00:00Z",
        "window": "PEAK",
        "predicted_success": 0.22,
        "reason": "Fixed +24h retry, no slot selection"
      }
    ],
    "expected_recovery_inr": 412.0,
    "basis": "modelled"
  },
  "sequenced": {
    "strategy": "SEQUENCED",
    "attempts": [
      {
        "attempt_no": 1,
        "slot_at": "2026-09-01T20:30:00Z",
        "window": "NON_PEAK",
        "predicted_success": 0.68,
        "reason": "Two days after predicted salary credit, non-peak window"
      }
    ],
    "expected_recovery_inr": 1104.0,
    "basis": "modelled"
  },
  "uplift_inr": 692.0,
  "uplift_basis": "modelled"
}
```

`window` is `PEAK` or `NON_PEAK`. Executions must be scheduled in non-peak windows. Both plans
are `modelled` — they are scorer output and are labelled as such wherever displayed.

For an unretryable mandate: `retryable: false`, `sequenced.attempts: []`,
`sequenced.expected_recovery_inr: 0.0`, and `router_verdict.reason` carries the explanation.
Zero scheduled retries against a revoked mandate is a demo beat, not an empty state.

### POST /api/chat

Cart recovery. Request:

```json
{ "conversation_id": "cnv_0007", "message": "can you do better on price?" }
```

Response:

```json
{
  "conversation_id": "cnv_0007",
  "messages": [
    { "role": "customer", "text": "can you do better on price?", "at": "2026-08-27T18:30:00Z" },
    { "role": "agent", "text": "I can hold your cart and cover shipping.", "at": "2026-08-27T18:30:03Z" }
  ],
  "cart_value_inr": 3980.0,
  "offer": {
    "requested_rung": "TIER_3_20_PCT",
    "granted_rung": "TIER_1_FREE_SHIPPING",
    "granted": false,
    "discount_inr": 0.0,
    "shipping_waived_inr": 79.0,
    "reason": "A 20% discount breaches the 18% margin floor on this cart.",
    "margin_floor_pct": 18.0,
    "decided_by": "policy_engine"
  },
  "done": false
}
```

`role` is `customer` or `agent`. The agent may **request** a rung on the offer ladder; the
policy engine grants or denies it and sets every rupee figure. `granted_rung` is authoritative —
the frontend renders that, never the requested one.

### POST /api/webhooks/razorpay

Razorpay test-mode events. Returns `200` with `{"ok": true, "case_id": "case_0417" | null}` as
fast as possible — detection runs after the response. A dropped webhook is simulated by not
calling this endpoint at all, which is what produces the live broken state on stage.

## 4. SSE — GET /api/cases/{case_id}/stream

`Content-Type: text/event-stream`. The reasoning trace for a case, streamed as the agent thinks.

**Emit events as they happen. Never buffer and flush at the end** — the point is that a judge
watches it think. Target pacing is roughly **850ms between events**: readable, not dumped.

Every event uses the SSE `event:` name and a JSON `data:` payload. All payloads carry:

```json
{ "case_id": "case_0417", "seq": 4, "at": "2026-08-27T18:30:04Z" }
```

`seq` starts at `0` and increments by one. Consumers render in `seq` order.

| event | additional payload fields |
|---|---|
| `thinking` | `text` |
| `tool_call` | `call_id`, `tool`, `args` |
| `tool_result` | `call_id`, `tool`, `ok`, `summary` |
| `guardrail` | the full `GuardrailResult` shape |
| `conclusion` | `break_type`, `text`, `recommended_action` (`Action`), `confidence` |
| `done` | `status` (`RESOLVED` \| `BLOCKED` \| `AWAITING_APPROVAL`), `duration_ms` |
| `error` | `code`, `message` |

Example:

```
event: guardrail
data: {"case_id":"case_0417","seq":7,"at":"2026-08-27T18:30:07Z","name":"refund_requires_terminal_payment","passed":false,"blocking":true,"message":"The payment is still PENDING...","evaluated_at":"2026-08-27T18:30:07Z"}
```

`tool_result.summary` is short — a sentence, not a JSON dump. Long tool output burns context and
produces worse reasoning.

`done` is always the last event, including after `error`. A stream that ends without `done`
must be treated by the frontend as a failure and rendered as such, not left spinning.

When `DEMO_MODE=replay` the same events are served from `frontend/src/mock/trace.json` at the
same pacing. That path stays working — it is the fallback if the LLM rate-limits mid-demo.

## 5. Errors

```json
{ "error": { "code": "CASE_NOT_FOUND", "message": "No case with id case_9999." } }
```

| HTTP | code |
|---|---|
| 400 | `INVALID_PARAMETER` |
| 404 | `CASE_NOT_FOUND`, `MANDATE_NOT_FOUND`, `CONVERSATION_NOT_FOUND` |
| 409 | `ACTION_BLOCKED_BY_GUARDRAIL` |
| 429 | `LLM_RATE_LIMITED` |
| 500 | `INTERNAL_ERROR` |

`ACTION_BLOCKED_BY_GUARDRAIL` carries `"blocked_by": ["<guardrail name>"]` alongside `message`.
A guardrail block is an expected outcome, not a server fault — it is never a `500`.

## 6. Mock fixture map

`frontend/src/mock/*.json` mirrors this contract exactly and is generated by `scripts/seed.py`
from the same rows written to SQLite. If the backend adds a field, the mock gets it in the same
commit. `VITE_USE_MOCK=true` must carry the entire demo unaided.

| fixture | mirrors |
|---|---|
| `summary.json` | `GET /api/summary` — the whole response |
| `waterfall.json` | the `waterfall` block alone, for `Waterfall.jsx` |
| `cases.json` | `GET /api/cases` — the whole response |
| `trace.json` | ordered array of SSE payloads, each with an `event` key, for replay |
| `mandates.json` | `GET /api/mandates` plus a `plans` map keyed by `mandate_id` |
| `conversations.json` | seeded `POST /api/chat` turns keyed by `conversation_id` |
